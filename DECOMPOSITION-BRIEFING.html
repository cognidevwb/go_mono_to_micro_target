What this costs you

2 method calls that cannot fail today become network calls that can. Each gets a typed HttpClient with a timeout, a retry and a circuit breaker — which is a mitigation, not a removal. This is the honest price of the boundary.

The order, and why

Leaves first, the hub last. A service with no outbound calls can be extracted and routed on its own; one that calls three others cannot be extracted until they exist. The riskiest cut happens once the cheap wins are already in.

  • 1. Orders Service — needs catalog-service, customers-service first
  • 2. Catalog Service — a leaf — nothing to wait for
  • 3. Customers Service — a leaf — nothing to wait for
  • 4. Inventory Service — a leaf — nothing to wait for
  • 5. Payments Service — a leaf — nothing to wait for

Considered and not applied

An architecture review that lists only what you did is half a review. These were evaluated against this repository and left out.

  • Backend for frontend — A single Go gateway is what this run scaffolds; per-client backends are a later refinement you add by hand.
  • Dapr — This run talks to NATS/Kafka and HTTP directly from Go; Dapr is an additional sidecar runtime nothing here installs.
  • Saga — choreography — needs coordination = choreography — you chose orchestration
  • Synchronous compensated call chain — needs event_backbone = none — you chose nats
  • Change data capture — needs migration_approach = parallel-run — you chose strangler
  • CQRS — needs read_write_model = cqrs — you chose crud
  • Durable execution — This platform generates a saga whose state lives in the orchestrating service’s own database — no extra runtime to operate. Durable execution (Temporal Go SDK) is the upgrade path when flows outgrow it.
  • Event sourcing — needs read_write_model = event-sourced — you chose crud
  • Materialized view / read model — needs read_write_model = cqrs — you chose crud
  • Read replica — needs at least 1 read_heavy_services — this run has 0
  • Read-through cache — needs at least 1 read_heavy_services — this run has 0
  • Try–Confirm–Cancel — TCC requires every participant to expose Try/Confirm/Cancel; this platform generates compensating sagas because a strangler extraction has participants (and a legacy monolith) that cannot be reshaped that way. Adopt it per participant where isolation is worth it.
  • Decompose by subdomain (DDD) — needs boundary_strategy = subdomain — you chose domain
  • Modular monolith first — needs at most 2 services — this run has 5
  • Parallel run — needs migration_approach = parallel-run — you chose strangler
  • Service-to-service identity — needs at least 6 services — this run has 5
  • Service mesh — needs at least 6 services — this run has 5
  • Sidecar / ambassador — Sidecarless (ambient / eBPF) meshes are displacing it, and nothing in this run scaffolds a sidecar.
  • Hexagonal (ports and adapters) — needs service_internal_structure = hexagonal — you chose flat-package

What happens next

The platform is generated first and compiles before any domain code exists. Your own code is then moved in verbatim — package clauses, import paths and the shared *gorm.DB split mechanically, nothing rewritten. Only the marked seams are implemented by a model, and only inside the markers. Each task compiles and commits on its own.

This run moved 954 lines verbatim and generated 404 deterministically, out of 1358 in total — 97% of the result before a model wrote anything. 12 seam points were left marked, across 5 client calls and 1 saga.

The map planned 2 cross-service calls and the porter marked 5. The difference is not an error on its own — a call can resolve inside one service once its code is together — but it is worth a look before you approve.

When it finishes, the git strategy you chose is applied: archive-and-adopt. Local git only — nothing is pushed anywhere.
