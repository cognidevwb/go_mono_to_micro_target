What it does

What this system does for the people who use it, and which files do it.

Written by a language model from this repository's structure. File paths are checked against the real file list; the wording is not reproducible between runs.

This is E-commerce order management (online shop backend split into catalog, customer, inventory, payment and order services behind a gateway).

This is the backend of an online shop. The shown code lets shoppers list products, register a customer account, look up a customer, place orders and list their orders. It lets staff add priced products, check stock for a product and look up the payments recorded for an order. Placing an order is the central flow.

When an order is placed, the order service checks that the customer is active. It reserves stock for each item, looks up each item's price from the catalog, then charges payment as the last step. The order is only committed once the charge succeeds, and a failure returns the failing step's own message. If a step fails, stock already reserved is released through an idempotent inventory compensation route. A payment-void route also exists in the payment service, but the shown order code does not call it. A declined charge writes no payment record.

The services are separate HTTP services. A gateway routes requests by path prefix and strips internal-caller headers from outside requests. It verifies bearer tokens only when an issuer is configured. An order-placed event is published and the inventory service consumes it without handling a message twice, but that handler only logs the payload. A scheduled restock job also runs. Evidence scope: the shown source excerpts. Deployment, monitoring and legacy-format conversion material is excluded, and nothing here is runtime-verified.

Place an order

Customer

A customer submits an order with one or more items and quantities. The shop rejects an invalid request or an inactive customer, reserves stock, prices the lines and charges payment last, and returns the placed order.

  1. Customer submits their id and items with positive quantities
  2. An invalid request is rejected with an error message
  3. The order service asks the customer service whether the account is active and refuses if it is not
  4. Stock is reserved for each item and its unit price is fetched from the catalog
  5. A pending order is saved and the total is charged through the payment service
  6. The order is marked placed and an 'order placed' event is published in the same transaction
  7. Any failure is returned to the customer as a conflict with the failing step's message

Evidence: POST /orders handler placeOrder; Service.PlaceOrder; saga.CreateOrder (inventory → payments); PlaceOrderRequest binding rules

Have a failed order release its reserved stock

Customer

When a step of order placement fails, completed steps are compensated in reverse order. Reserved stock is released through an idempotent inventory route and the customer sees the step's own error such as 'out of stock'. The payment service also has a route that voids captured payments, but the shown order code does not call it.

  1. A step fails, for example stock is short or the charge is declined
  2. The saga compensates completed steps in reverse order
  3. Reserved quantities are released through inventory's compensation route, keyed by saga id and product
  4. The order transaction rolls back so no order is left behind
  5. The customer receives the failing step's message

Block ordering for inactive customers

Customer

Before an order proceeds, the order service asks the customer service whether the account is active, and an inactive customer is refused. The call is retried with backoff on transport or server errors.

  1. The order service calls the customer service's is-active route
  2. The customer service looks up the account and returns its active flag
  3. An inactive account stops the order with 'customer inactive'

Price order items from the catalog

Customer

Each ordered product's unit price comes from the catalog and the line totals are summed into the order total. The catalog may serve a price from a per-instance cache for up to 30 seconds.

  1. The order service asks the catalog for each product's price
  2. The catalog returns the price, or not found for an unknown product
  3. The price is stored on the order line and added to the total

Reserve stock for ordered items

Customer

Stock is reserved for a product only if on-hand minus reserved covers the quantity, and the stock row is locked during reservation. The inventory service also consumes order-placed events without reprocessing a redelivered message, but its handler only logs the payload.

  1. The order service asks inventory to reserve a product quantity
  2. Inventory locks the stock row and checks available units
  3. The reserved count is increased, or a not-reserved answer is returned
  4. An unknown product returns not found
  5. Order-placed events are de-duplicated by message id before being logged

Pay for an order

Customer

A charge is validated, the external payment provider is asked to capture it, and a captured payment record is saved in the same transaction. A provider decline is reported as an error and no record is saved.

  1. The order service posts the order id and amount to payments
  2. The request is rejected if the order id is missing or the amount is negative or not a number
  3. The payment gateway is asked to capture the amount
  4. On success a captured payment is saved
  5. On decline an error is returned and nothing is saved

Use the shop through a single authenticated entry point

Customer

The gateway routes requests by longest path prefix to the catalog, customer, inventory, payment and order services. When an issuer is configured, it requires a valid bearer token. It strips internal-caller headers so outsiders cannot pose as services.

  1. A caller sends a request to the gateway
  2. When an issuer is configured, a missing or invalid bearer token gets 401
  3. The internal-caller and token headers are removed from the request
  4. The request goes to the service with the longest matching prefix, otherwise to the legacy upstream or 404
